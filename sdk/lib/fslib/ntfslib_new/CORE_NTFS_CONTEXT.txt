1. Mapping-pair encoder interop fix (src/filerecord/attributes/addattr.cpp):
   run LENGTHS were sized as unsigned variable-length integers, so any run
   whose top stored length byte had the sign bit set (for example 253
   clusters encoding as one byte 0xFD) decoded as a negative length in
   NTFS-3G, the Linux kernel driver, and Windows, which reject the runlist
   with EIO. Lengths now use the same signed byte sizing as LCN deltas
   (LengthMappingBytes) in GetMappingPairsSize, EncodeMappingPairs, and
   GetMappingPairEntrySize, with Length > MaximumPositive guards. The
   decoder (findattr.cpp) now rejects sign-bit-set stored lengths as
   corrupt, matching the other implementations. Round-trips through our
   own decoder had masked this; fragmented allocations through scattered
   1 MiB holes reproduced it deterministically, and the fix was verified
   3/3 with byte-identical ntfscat reads of an 11-extent file.

2. benchmark_core.sh widened with three alternately-ordered median rows,
   each gated on cross-implementation byte equality before timing:
   smallread (fresh exact lookup + resident read), fragread (dedicated
   64 MiB image whose free space is shredded into holes; NTFS-3G's own
   allocator returns ENOSPC for that layout, ntfslib's fragmented
   fallback allocates it, NTFS-3G verifies the bytes), and mutate
   (1 MiB overwrite, --write versus ntfscp, consistency-checked after
   timing). First sample set (CPU 12, powersave): directory 1.30x,
   read 1.39x, smallread 0.99x, fragread 1.50x, mutate 1.09x, all
   ntfslib leading except the smallread tie. Phase isolation showed the
   fresh-process rows are launch-bound (~2.6 ms floor): beyond its own
   usage-print baseline ntfslib's smallread work is ~0 ms versus
   ntfscat's ~0.6 ms, and its 1 MiB mutate work ~0.36 ms versus
   ntfscp's ~2.1 ms, so per-operation core work leads by large factors
   that the fresh-process protocol cannot display. Cold-open rows were
   rejected: without root cache drops, launch overhead swamps device
   reads. benchmark_fuse.sh order bias: the script measures ntfslib
   first, and under powersave the second-measured tool gains up to ~2x
   on read rows; only the listing row (ntfslib 2.5-2.9x) survives order
   reversal, cached reads tie at matched frequency, direct reads are
   approximately tied.

3. Writable FUSE mount (linux/fuse/ntfslib_fuse.cpp): mounts remain
   read-only by default; an explicit --writable flag enables create,
   mknod, mkdir, unlink, rmdir, rename (including POSIX replace via
   non-atomic remove-then-rename, RENAME_NOREPLACE honored,
   RENAME_EXCHANGE refused), link, write, truncate, fallocate
   (grow-only), utimens, chmod/chown (accepted and discarded like
   unmapped NTFS-3G), flush/fsync no-ops. Writable opens use direct_io
   so no stale kernel pages survive truncates; the directory listing
   cache is shared_ptr-owned with a releasedir hook and is cleared on
   every namespace mutation. Every mutation hook returns EROFS unless
   --writable was given. This matches NTFS-3G's actual guarantee level
   (ordered publication, no journal replay, dirty images left to
   chkdsk); crash atomicity still requires LFS, so writable mounts stay
   restricted to disposable images. Native NTFS EAs additionally surface
   as individual user.* xattrs (getxattr/setxattr/listxattr/removexattr
   with case-insensitive names, XATTR_CREATE/XATTR_REPLACE semantics,
   UINT8/UINT16 name/value limits); NTFS-3G only exposes the packed
   blob through system.ntfs_ea. The mount smoke test verifies the
   xattr round-trip through python3, the --ea direct command, and the
   system.ntfs_ea blob on a real NTFS-3G mount. posix_bench gained an
   amortized small_read sweep row (open+read+close of every small file
   per pass inside one process) so per-operation lookup cost is
   comparable without fresh-process launch overhead. That row initially
   showed NTFS-3G 1.33x ahead (90.7k versus 68.1k opens/s) because the
   mounted frontend re-walked the $I30 tree on every open and the no-op
   flush hook cost one FUSE round trip per close; read-only mounts now
   reuse validated records through a mount-lifetime RecordCache (the
   low fh bit marks cache-owned records so release skips destruction;
   writable mounts bypass the cache because mutation invalidation would
   dangle open handles), and flush is no longer registered. With the
   cache the amortized row flipped: ntfslib 163,434 versus NTFS-3G
   89,740 opens/s (1.82x ahead) with directory listing at 3.17x, so
   every FUSE row whose cost the filesystem controls now leads
   (cached/direct sequential reads remain kernel/page-cache-bound and
   approximately tied at matched frequency).

4. New test linux/tests/mount_write_smoke.sh (ntfslib_linux_mount_write,
   16th registered test): drives a --writable mount with ordinary POSIX
   tools while mirroring every operation into a host twin directory
   (mkdir trees, cp, appends, offset overwrites, 20-file bursts,
   truncate shrink/grow, all four rename shapes including directory
   rename and replace, hardlink, rm, rmdir, populated-rmdir refusal,
   utimens), diffs the mounted tree against the twin, then verifies
   independently after unmount: ntfsfix -n, ntfscat byte compares
   (including through the hard link), ntfsls name equality, and a full
   recursive diff plus timestamp check through a real read-only NTFS-3G
   mount. Passes under Release and ASan/UBSan. On this host AppArmor
   denies fusermount3 MOUNTS (not just unmounts) under /var/tmp, so
   mount tests take NTFSLIB_BENCH_ROOT for an owned mount root; without
   it they skip with exit 77.

5. New test linux/tests/fuzz_smoke.sh (ntfslib_linux_fuzz, 17th
   registered test): deterministic seeded bit-flip corruption of a valid
   image (85% of flips in the metadata-bearing first 4 MiB), 150
   variants by default (NTFSLIB_FUZZ_ROUNDS), five frontend commands per
   variant (--probe, --list, --list-info, --cat, --streams); any
   termination by signal or sanitizer abort fails the test, so the ASan
   tree turns memory errors into failures. The same variants are fed to
   ntfsls/ntfscat for comparison (crashes counted, never failing). This
   is the first standing fuzz gate; the deeper structure-aware fuzzing
   items in P1 remain open.

6. New test linux/tests/crash_consistency_smoke.sh
   (ntfslib_linux_crash_consistency, 18th registered test): SIGKILLs the
   --writable mount daemon between acknowledged operation batches (four
   rounds) and once mid-write with a background appender. After every
   kill the volume must pass ntfsfix -n, every acknowledged byte must
   read back exactly through ntfscat, remounting must succeed, and the
   final volume must be fully readable through a real NTFS-3G mount.
   This demonstrates a writable guarantee NTFS-3G does not make: its
   buffered metadata dies with the daemon, while the shared core
   publishes each mutation synchronously in a readable order. This is
   acknowledged-operation daemon-crash durability, not host power-loss
   atomicity - LFS remains the roadmap item for journaled recovery.

7. Index reclamation parity measured (2026-07-25): identical churn (one
   directory, create 400, delete 360) driven through our direct commands
   and through a real writable NTFS-3G mount left byte-identical index
   footprints on both volumes per ntfsinfo: $INDEX_ROOT 56 bytes,
   $INDEX_ALLOCATION 81,920 bytes allocated, $BITMAP 8 bytes. NTFS-3G
   does not merge underfull index nodes either; the "merge/rebalance"
   roadmap item is an improvement beyond both implementations, not a
   deficit against NTFS-3G.

8. LZNT1 compressor landed (compressed-write tranche, phase 1 of 3):
   NtfsCompressLznt1 in src/filerecord/read/compression.cpp beside the
   decoder, with public NtfsLznt1Compress/NtfsLznt1Decompress wrappers.
   Greedy hash-chain matcher (4096 buckets, 64-step chains, minimum
   match 3), per-chunk raw fallback when a chunk does not shrink, the
   decoder's exact position-dependent displacement/length split, and
   STATUS_BUFFER_TOO_SMALL when the stream exceeds OutputCapacity so
   unit writers can demand a cluster saving and fall back to raw
   storage. One portability trap already caught and fixed: the hash
   multiplier literal was UL (64-bit on Linux hosts), overflowing the
   bucket index; width is now pinned to UINT32. Verified by the 19th
   registered test ntfslib_linux_lznt1_roundtrip: 264 deterministic
   corpora (zeros/text/random/sawtooth at 16 sizes from 1 byte to
   100000, plus 200 mixed run/noise buffers) byte-exact through
   compress+decompress under Release and ASan/UBSan, shrink asserted
   for compressible corpora, tight-capacity rejection asserted for
   random data.

   Phases 2 and 3 landed the same day. FileRecord::WriteCompressedData
   (filedata.cpp) rebuilds the complete unit grid on write: the current
   plaintext is materialized through the verified read path, patched,
   and recompressed unit by unit; a unit that saves at least one
   cluster stores its compressed form with a sparse tail, a unit that
   does not shrink stores all sixteen clusters raw, new clusters and
   data become durable before the one-record mapping swap commits, and
   old clusters are released afterwards. ReplaceNonResidentMappingPairs
   and BuildNonResidentMappingSegment now accept exactly-ATTR_COMPRESSED
   attributes (CU=4, unit-aligned allocation) and emit the 0x48 header
   with the physical CompressedDataSize; every layout conditional that
   keyed on ATTR_SPARSE now keys on any nonzero derived flag. The
   supported shape is deliberately narrow - base-record $DATA flagged
   exactly ATTR_COMPRESSED, CU=4, no $ATTRIBUTE_LIST, stream bounded to
   4 MiB (whole-grid rebuild) - and every other shape keeps the
   previous unsupported result. Truncate/allocation-size paths for
   compressed streams remain unimplemented.

   The 20th registered test, compressed_write_smoke.sh
   (ntfslib_linux_compressed_write), has NTFS-3G author a genuinely
   compressed file (directory +C via system.ntfs_attrib through a real
   ntfs-3g mount), then drives four core writes - unaligned mid-unit
   incompressible patch, two-unit span, EOF growth, and an all-zeros
   rewrite that must recompress below 16 KiB physical - verifying every
   state byte-for-byte through ntfscat (NTFS-3G's decoder over our
   encoder and unit layout: the interop proof), our own reader, and
   ntfsfix -n.

9. Security descriptor mutation landed (first tranche):

0. DEVELOPMENT POLICY
=====================

The shared NTFS implementation is the product. FUSE is only a Linux test
surface.

Priority order:

1. Correct on-disk NTFS behavior, corruption rejection, and complete reads.
2. Correct allocation, attribute mutation, file creation, directory mutation,
   and metadata consistency.
3. LFS transaction logging, replay, recovery, and crash atomicity.
4. Per-volume environment state, concurrency, and shared-core performance.
5. ReactOS driver integration.
6. FUSE conveniences only when they improve testing of the shared core.

Do not optimize a FUSE-only cache and present it as an NTFS-core result.
Core benchmarks must use the mountless image commands and compare names and
bytes with independent ntfs-3g tools before timing.

Writable tests are allowed only on disposable images. There is no safe
writable mount until LFS logging and recovery are implemented.

What is implemented and verified:

* Allocate, initialize, publish, deallocate, and roll back ordinary base MFT
  file records through the shared extension-record allocator.
* Initialize a new regular file with:
  - V1 $STANDARD_INFORMATION
  - indexed POSIX $FILE_NAME
  - an empty unnamed resident $DATA attribute
  - inherited compact resident legacy security where applicable
* Initialize a new directory with a valid empty $I30 $INDEX_ROOT and,
  matching Windows, no default ARCHIVE attribute.
* Validate the final filename, parent path, attributes, duplicate-name state
  (volume $UpCase collation), and parent directory.
* Publish a new file through a public counted UTF-16 creation API:

      NtfsMasterFileTableCreateFile

* Insert directory index entries in every tree shape:
  - growth inside the resident root;
  - first-overflow push-down of the complete root list into index buffer 0,
    creating $BITMAP and promoting a fresh nonresident $INDEX_ALLOCATION in
    one record commit after the root shrinks in memory;
  - in-place leaf insertion;
  - median splits of full nodes with right-node-first publication;
  - recursive parent insertion along the recorded descent path;
  - root push-down at any depth.
* Update the parent directory last-write/change timestamps.
* Supply portable global new/delete forms required by the new native code.

Write-path fixes that fell out of verification:

* MasterFileTable::WriteFileRecordToMFT snapshots the fixup-committed image
  and immediately restores the live record. Writing $MFT record 0 through
  its own fixup-scrambled buffer corrupted the attribute walk once mapping
  growth moved $BITMAP bytes across a sector tail, splitting record 0 from
  $MFTMirr after 1,065 same-directory creations.
* PromoteResidentData accepts TypeIndexAllocation.
* The unable-to-write diagnostic includes the failing record number.

The same day added the namespace tranche (src/mft/namespace.cpp plus $I30
removal in editdir.cpp):

* Directory index removal for every tree shape: root and leaf cuts,
  internal entries replaced by their subtree's collation maximum with
  END-child rewiring, END-only chain release, and replacement overflow
  through the shared split-and-promote path.
* NtfsMasterFileTableDeleteFile with Win32 DeleteFile/RemoveDirectory
  semantics, DOS/WIN32 alias pairs, hard-link counting, and full
  record/cluster teardown on the last name (runs captured before records
  blank, clusters released last).
* NtfsMasterFileTableRenameFile: same-directory, cross-directory, and
  case-only renames; collision checks exempt only the file itself; one
  shared parent object when source and destination coincide.
* NtfsMasterFileTableCreateHardLink with rollback; $FILE_NAME is the one
  unnamed attribute type allowed to repeat in a record.
* Per-directory scaling: WriteFileData creates the initial
  $ATTRIBUTE_LIST proactively while the base record has headroom
  (ordinary records only) so $INDEX_ALLOCATION segments relocate to
  extension records, and $MFT growth reserves 16-cluster chunks to keep
  record 0 compact. 5,000 single-directory creations verified; drains
  reclaim everything but the permanent MFT chunks.
* Frontend: --remove, --remove-dir, --rename, --link; test
  ntfslib_linux_namespace.

Remaining limits of this tranche:

* Create/split/remove publication is not crash-atomic without LFS;
  publication order merely keeps every intermediate on-disk state
  readable.
* Removal never merges underfull nodes; it only releases END-only
  chains. Long-lived churn can leave sparse index buffers.
* SecurityId inheritance for NTFS 3.x creation is not implemented.


3. SHARED-CORE ACHIEVEMENTS
===========================

3.1 Metadata validation and safe I/O
------------------------------------

Implemented:

* Positioned reads and writes in Linux, ReactOS user mode, and kernel mode.
* NTFS legal sector-size validation.
* Exact 64-bit boot geometry.
* Strong MFT record signature, bounds, alignment, attribute-layout, and
  update-sequence validation.
* Shared fixup application/commit logic.
* Correct $MFTMirr bootstrap and distinct main/mirror targeting.
* Corrupt runlist rejection without assertions or out-of-volume access.
* Sparse mapping-pair decoding.
* Zero reads for sparse holes and uninitialized tails.
* Cached decoded runlists for open records and MFT metadata.
* Correct free-cluster calculation from $Bitmap in bounded chunks.
* Validated literal volume-bitmap queries.
* Validated retrieval-pointer queries with sparse LCN -1 reporting.
* Validated downward in-use MFT record enumeration.

3.2 Names, lookup, and directories
----------------------------------

Implemented:

* Bounded NT/DOS wildcard matching.
* Volume $UpCase-based filename collation.
* Correct multi-level $I30 traversal.
* Correct in-order separator-key enumeration.
* $I30 bitmap validation and child VCN cycle/duplicate rejection.
* Exact lookup with lazy collation-selected child descent.
* Bulk enumeration with one index-allocation/bitmap read and arena-backed keys.
* Namespace-based DOS alias handling instead of quadratic guessing.
* Case-insensitive nested path lookup.
* Intermediate/final reparse detection with counted unparsed suffixes.
* File and directory creation with full $I30 insertion: resident-root
  growth, first-overflow root push-down, leaf insertion, median node
  splits, recursive parent promotion, and root push-down at any depth.

Verified large-directory case:

* A 1,001-entry directory returned all 1,001 entries.
* The older traversal returned only 261 entries.
* Mixed-case left/middle/right exact lookups matched ntfs-3g.
* An $INDEX_ROOT moved to an extension record was found through
  $ATTRIBUTE_LIST.

3.3 $ATTRIBUTE_LIST and fragmented streams
------------------------------------------

Implemented:

* Extension-record lookup with sequence-number and base-reference validation.
* Attribute ID, type, name, flag, and VCN validation.
* Ordered contiguous merging of nonresident stream segments.
* Composite runlist caching.
* Validation that $ATTRIBUTE_LIST's own mapping pairs remain resolvable from
  the base record.
* Nonresident list growth.
* Copy-on-write compaction of fragmented list storage.
* Mapping-pair continuation records for base-owned streams.
* Mapping-pair continuation records for extension-owned streams.
* Staged publication and rollback of list/extent changes.
* Collapse back to a VCN-zero owner and release obsolete MFT records.

Verified examples include:

* A 10,813,440-byte fragmented stream split across MFT records 568 and 570
  matched ntfscat byte-for-byte.
* 128 alternating base-stream runs crossed into a continuation record and
  later collapsed back to resident zero length.
* 384 alternating extension-stream segments were reconstructed and mutated.
* A 4,072-byte list grew across a 4 KiB boundary.
* An 8,152-byte two-run list was compacted copy-on-write to one 12,288-byte
  allocation.
* MFT bitmap ownership and old-cluster release were independently checked.

---------------------------------------------

Implemented:

* Resident reads and exact resident replacement.
* Resident shrink/growth with complete tail relocation and 8-byte alignment.
* Resident-to-nonresident promotion.
* Existing nonresident in-place writes across run boundaries.
* Nonresident extension with contiguous-first, fragmented fallback allocation.
* Mapping-pair re-encoding and continuation.
* Zero-filled logical gaps.
* Initialized-size semantics.
* EOF growth/shrink and whole-tail cluster release.
* Zero-length demotion to resident.
* FileAllocationInformation-style preallocation independent of EOF.

Independent checks use ntfscat, ntfsinfo, ntfscluster, literal $Bitmap reads,

7. BENCHMARK STATUS AND RETEST METHOD
=====================================

7.1 Core benchmark is authoritative
-----------------------------------

The current recorded mountless Release sample used:

* A 384 MiB NTFS 3.1 image.
* 250 small files.
* One 64 MiB ordinary uncompressed stream.
* Equal 251-name output.
* Exact equal stream bytes.
* One untimed warm-up per tool.
* CPU 0 pinning.
* 100 fresh directory command invocations.
* Three fresh stream command invocations.
* Warm host page cache.
* New process and volume object per invocation.

Recorded result:

    Fresh open + directory enumeration
      ntfslib: 2,051.35 operations/second
      ntfsls:  1,118.03 operations/second
      ratio:   ntfslib 1.84x

    Fresh open + cached sequential read
      ntfslib: 9,885.20 MiB/second
      ntfscat: 4,834.32 MiB/second
      ratio:   ntfslib 2.05x

This is one regression sample, not a statistical claim.

The local comparison target is:

    ntfs-3g 2022.10.3 integrated FUSE 28

The benchmark must be rerun after the current uncommitted creation work is
built and tested. Do not reuse the numbers as proof for the unverified WIP.

7.2 Required core benchmark retest rules
----------------------------------------

Before timing:

1. Build Release with static C++ support enabled.
2. Generate one image used by both implementations.
3. Confirm both return the exact same visible names.
4. Compare the complete test stream byte-for-byte.
5. Warm each tool once.
6. Pin the coordinator to one CPU.
7. Alternate tool order between samples to reduce frequency/order bias.
8. Take at least five samples and report the median.
9. Record CPU, kernel, compiler, ntfs-3g version, image geometry, and command.
10. Keep directory/open and sequential-read results separate.
11. Do not mix compressed, sparse, resident, and ordinary streams into one
    unlabeled throughput number.

The workload is scripted as linux/tests/benchmark_core.sh:

    linux/tests/benchmark_core.sh \
      /var/tmp/ntfslib-linux-release/fuse/ntfslib_fuse

It creates the shared fixture, refuses to time until names and bytes match,
pins every timed launch with taskset (NTFSLIB_BENCH_CPU, default 0),
alternates ntfslib and ntfs-3g order across at least five samples, emits raw
CSV plus medians, never mounts, and preserves the fixture only on failure.

The 2026-07-24 post-creation rerun (powersave governor with a 0.8 GHz
floor, ~1.0 background load, NTFSLIB_BENCH_CPU=12, ntfs-3g 2022.10.3)
reported medians of 788.14 versus 566.01 ops/s for directory enumeration
(1.39x) and 4,398.32 versus 3,391.45 MiB/s for cached sequential reads
(1.30x). The post-namespace nine-sample rerun the same day reported
337.95 versus 270.55 ops/s (1.25x) and 2,813.39 versus 2,013.80 MiB/s
(1.40x) under a post-build thermal sag; ntfslib led both metrics in
every sample set. Absolute rates are frequency-limited and not comparable with the
recorded boosted sample; the direction is unchanged. A CPU 0 run under the
same governor showed launch-noise variance large enough to flip the
directory ratio, so record governor and pin conditions with every sample.

7.3 FUSE benchmark is diagnostic, not a core claim
---------------------------------------------------

Existing command:

    TMPDIR=/var/tmp \
    NTFSLIB_BENCH_ROOT=/home/ahmed/WorkDir/TTE \
    sdk/lib/fslib/ntfslib_new/linux/tests/benchmark_fuse.sh \
      /var/tmp/ntfslib-linux-release/fuse/ntfslib_fuse \
      /var/tmp/ntfslib-linux-release/ntfslib_posix_bench

The script validates entry counts and stream bytes, then reports listing,
cached-read, and direct-I/O rows.

Earlier FUSE context:

* Directory caching can make ntfslib substantially faster.
* Direct reads were approximately tied.
* Cached reads were controlled mostly by the Linux kernel.
* One older sample showed ntfs-3g 1.61x ahead on cached reads.

These rows describe frontend/kernel behavior and must not override the
mountless shared-core comparison.
